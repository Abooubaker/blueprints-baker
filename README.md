# Blueprints Baker

**An AI-assisted robotics engineering platform.** Describe the robot you want to build, and
Blueprints Baker turns the idea into a structured specification, a compatible bill of materials, wiring,
firmware, a mechanical plan, and a realistic budget.

> **Project status: end-to-end build (v0.1.0).** A guided flow turns a description into a named,
> confirmed robot, then generates sourced part prices, a validated pin-level schematic, multi-file
> code scaffolds, a parametric STL with JOD print pricing, a budget, and a documentation set.
> The engine is deterministic and offline; authentication and live supplier feeds are still
> planned. See the [roadmap](docs/roadmap.md) and
> [GitHub Project board](https://github.com/users/Abooubaker/projects/1).
>
> **Hosted API:** deploy the FastAPI service with [Render + Neon](docs/deployment.md). The web app
> talks to it through `NEXT_PUBLIC_API_URL`; no credentials ship in the browser bundle.

> **Live demo:** <https://abooubaker.github.io/blueprints-baker/> — a read-only Pages build generated
> by the same deterministic engine. See [docs/demo-site.md](docs/demo-site.md).

### Hosted product

The read-only demo cannot create projects. For the full product, deploy the API and web app:

1. Create a Neon PostgreSQL project and copy the pooled connection string.
2. Deploy the API to Render from `render.yaml` (Docker) with `DATABASE_URL` and `CORS_ORIGINS`.
3. Deploy the web app to Render (Node) with `NEXT_PUBLIC_API_URL` pointing at the API.

[`docs/deployment.md`](docs/deployment.md) has the exact settings, order of operations, and
troubleshooting. Migrations run once per container deploy; production disables the interactive
`/docs` routes.

## Why Blueprints Baker

Building a robot from scratch means juggling five coupled decisions: what to build, which parts fit
together, how to wire them, how to program them, and whether the result fits the budget. Mistakes
are expensive and usually discovered after the parts arrive.

Blueprints Baker keeps those decisions in one typed project workspace. Each specialized AI agent owns one
artifact and consumes the artifacts produced before it. That makes the output inspectable, lets a
human correct any step, and keeps the system provider-independent — no vendor SDK leaks into the
domain layer.

| Provider-independent agent contracts and JSON Schema export | ✅ Implemented |
| Deterministic orchestrator with dependency resolution, artifact ownership, and audit persistence | ✅ Implemented |
| Planner, component research, and electrical agents | ✅ Implemented (deterministic) |
| Schematic & pinout: every pin and destination, nets, power budget, validation, CSV/SVG/Markdown/JSON exports | ✅ Implemented |
| KiCad netlist and KiCad schematic exports (importable by EasyEDA Pro and KiCad) | ✅ Implemented |
| Programming agent: multi-file code bundles for Python, C++, C, STM32 assembly, Verilog, VHDL | ✅ Implemented (scaffolds) |
| Mechanical agent: parametric STL, printed weight, PLA/PETG/ABS/Resin/TPU JOD chart | ✅ Implemented |
| Cost agent: JOD/USD roll-up, budget status, alternatives | ✅ Implemented |
| Documentation generator: overview, sourcing, wiring, firmware, mechanical, safety, decisions, budget | ✅ Implemented |
| Store pricing from six curated stores (Temu, mikroelectron, waslleh, Amazon, AliExpress, ghanimjo) | ✅ Estimates, cheapest-first |
| Static GitHub Pages demo generated by the same engine | ✅ Implemented |
| Authentication, live supplier feeds, model-backed agents, collaboration | 📋 Planned |

The engine is deterministic, not model-backed: the same specification and preferences produce the
same build, and every finding is reproducible offline. Code bundles are runnable scaffolds with
explicit TODO blocks, not finished firmware; store prices are curated JOD estimates, not live
quotes.

## Stack

| Layer | Choice | Why |
| --- | --- | --- |
| Web | Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4 | Server-first rendering for marketing pages, client components only where interaction is needed, one toolchain for UI and API types. |
| API | Python 3.12, FastAPI, Pydantic 2 | Async I/O, first-class OpenAPI generation, and validation shared by the HTTP and agent layers. |
| Data | PostgreSQL 16, SQLAlchemy 2 (async), Alembic | Relational integrity for coupled engineering artifacts, JSONB-ready flexible fields, reversible migrations. |
| AI | Provider-independent `LLMProvider` boundary, typed agent contracts | Swap OpenAI/Anthropic/local models without touching domain code; validate model output before it enters the graph. |
| Tooling | uv, npm, Ruff, mypy (strict), pytest, ESLint, Prettier, GitHub Actions | Fast, reproducible installs on both sides of the monorepo and meaningful CI gates. |

## Quick start

### Prerequisites

- Python 3.12+ and [uv](https://docs.astral.sh/uv/)
- Node.js 20.9+ and npm 10+
- PostgreSQL 16 (local install or Docker)

### 1. Start PostgreSQL

```bash
docker compose up -d db
# or point DATABASE_URL at an existing PostgreSQL instance
```

### 2. Run the API

```bash
cd apps/api
cp .env.example .env
uv sync
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --port 8000
```

- API: <http://localhost:8000>
- OpenAPI UI: <http://localhost:8000/docs>
- Readiness: <http://localhost:8000/health/ready>

### 3. Run the web app

```bash
cd apps/web
cp .env.example .env.local
npm ci
npm run dev
```

Open <http://localhost:3000>, choose **New project**, describe a robot, and follow the six steps.
The last step creates the project, saves your answers, runs the full build, and opens the results.

### 4. Run the quality gates

```bash
make check          # backend lint/types/tests + frontend lint/types/format/build
# or individually
make api-check
make web-check
```

See [docs/development.md](docs/development.md) for the full setup, test strategy, contract workflow,
and troubleshooting guide.

## API at a glance

```bash
curl http://localhost:8000/health/ready

curl -X POST http://localhost:8000/api/v1/projects \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Science Fair Line Follower",
    "description": "Follows a black tape track and stops at obstacles.",
    "robot_type": "line_follower",
    "difficulty": "beginner",
    "target_platform": "arduino",
    "budget_max_usd": 60
  }'
```

Project creation bootstraps a draft specification. Running agents on the project returns the
orchestration audit trail:

```bash
curl -X POST http://localhost:8000/api/v1/projects/<project-id>/agent-runs \
  -H 'Content-Type: application/json' -d '{"agents": ["robot_planner"]}'
```

Generate the electrical plan and download an export:

```bash
curl -X POST http://localhost:8000/api/v1/projects/<project-id>/electrical
curl -OJ http://localhost:8000/api/v1/projects/<project-id>/electrical/export/kicad-netlist
```

Run the guided-build pipeline directly:

```bash
curl -X POST http://localhost:8000/api/v1/intent/identify \
  -H 'Content-Type: application/json' \
  -d '{"description":"A patio rover that avoids obstacles and sends distance over Wi-Fi"}'

curl -X PUT http://localhost:8000/api/v1/projects/<project-id>/preferences \
  -H 'Content-Type: application/json' \
  -d '{"description":"…","robot_name":"Patio Scout","robot_type":"rover","difficulty":"beginner","shops":["temu","mikroelectron","waslleh","amazon"],"languages":["python","cpp"],"controllers":["ESP32"],"custom_pcb":false,"confirmed":true}'

curl -X POST http://localhost:8000/api/v1/projects/<project-id>/build
```

See [docs/api.md](docs/api.md) for the plan contract, build artifact, and export formats.

## Development workflow

1. Pick an issue from the [Project board](https://github.com/users/Abooubaker/projects/1).
2. Branch from `main` (`feat/…`, `fix/…`, `docs/…`).
3. Implement with tests; keep the API contract in sync (`make contracts`).
4. Run `make check` and open a pull request using the template.
5. A change is done when CI is green, docs are updated, and the issue is moved to **Done**.

Read [CONTRIBUTING.md](CONTRIBUTING.md) before your first pull request.

## Limitations

- No authentication or authorization yet; `owner_id` is nullable by design.
- Agents are deterministic and curated; they do not call an LLM. Identification, part selection,
  and pricing understand the bundled catalog and store estimates only.
- Store prices are curated JOD planning estimates, sorted cheapest-first. They are not live quotes;
  confirm stock, price, and shipping before ordering.
- Generated code is a multi-file scaffold with explicit TODO blocks, not production firmware.
  Verify every pin assignment on hardware. STM32 assembly and HDL bundles are interface sketches.
- The 3D model is a parametric reference chassis for weight and print-price estimation, not a
  manufacturable enclosure. Onshape integration remains optional and unconfigured.
- The electrical netlist is structural (nets/pins), not a routed PCB; imported symbols must be
  reviewed before layout.
- The component catalog has no seed data and supplier integrations do not exist.
- The Docker Compose file is a convenience for PostgreSQL; the production API image is built in CI.
- SQLite is supported for tests only; PostgreSQL is the supported runtime database.
